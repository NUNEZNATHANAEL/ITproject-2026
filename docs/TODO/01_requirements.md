TODOアプリ 要件定義書（V1）
1. 目的・対象範囲
目的
既存のExpress＋TypeScript＋EJS構成のWebサイトに、Neon PostgreSQLをデータストアとするシンプルなTODO管理機能を追加する。

対象範囲（V1）

画面およびルーティング: 既存の / および /api/db-check を維持したまま、新規画面を /todo に配置する。画面からは Fetch を用いてREST APIを操作する（TodoApi クラスへの分割や実際のファイル配置は「要確認」とし、設計書にて決定する）。

データベース・インフラ: 学生自身のNeon PostgreSQL（既存のDB接続と環境変数 DATABASE_URL を利用。使用ライブラリ等の詳細は「要確認」とし設計書で決定）を使用し、Vercelへ公開する。Preview環境とProduction環境は同一のNeon DBを参照する。

データポリシー: 個人情報は一切扱わず、検証・運用ともに架空のデータのみを使用する。

スコープ外（V1では実装しない機能）: ユーザー認証・認可、優先度設定、一覧の絞り込み・検索、登録済みタイトルの更新。

2. 4機能と受け入れ条件
ベースURLは /api/v1/todos とする。

REQ-01: 一覧取得（GET /api/v1/todos）
操作: 画面（/todo）の初期表示時、または再読み込み時にTODO一覧を取得する。

入力: なし。

結果: 登録済みのTODO配列をステータスコード 200 で返却する。データが0件の場合は 200 で data: [] を返す。

エラー: DB接続不可時は 503、サーバー内部エラー時は 500 を返す。

受け入れ条件: 登録済みの全TODOが画面に表示されること。0件時もエラーにならず空のリストとして正常表示されること。

確認方法: /todo にアクセスし、DB内のレコード（および0件状態）と画面表示が一致することを確認する。

REQ-02: 新規登録（POST /api/v1/todos）
操作: 画面の入力フォームからタイトルを送信し、新しいTODOを追加する。

入力: title（文字列）。前後の空白（トリム）を除いて1〜100文字であること。

結果: 未完了状態でTODOを作成し、ステータスコード 201（または共通仕様に準拠した成功ステータス）で作成データを返す。

エラー: リクエスト形式不正は 400、文字数制限違反（0文字または101文字以上）や型不正は 422、DB接続不可時は 503、サーバー内部エラー時は 500 を返す。

受け入れ条件: 1〜100文字のタイトルで登録でき、画面に反映されること。空白のみや101文字以上の入力が拒否され、エラー表示されること。

確認方法: 正常値（1文字、100文字、前後空白あり）と異常値（空白のみ、101文字）を入力し、登録可否とレスポンスコードを確認する。

REQ-03: 完了状態の部分更新（PATCH /api/v1/todos/:id）
操作: 画面上のチェックボックス等から、対象TODOの完了状態（完了／未完了）を切り替える。

入力: パスパラメータ id（1以上の整数）、リクエストボディに完了状態フラグ（真偽値）。

結果: 該当IDの完了状態のみを更新し、ステータスコード 200 で更新後のデータを返す。

エラー: id が1以上の整数でない場合やボディ形式不正は 400、完了状態の型不正などは 422、該当IDが存在しない場合は 404、DB接続不可時は 503、サーバー内部エラー時は 500 を返す。

受け入れ条件: 対象TODOの完了・未完了が切り替わり、リロード後も状態が維持されること。タイトルなど他の項目は変更されないこと。

確認方法: 画面上で完了状態を切り替え、ページ再読み込み後も状態が保持されていること、および存在しないID指定時の 404 応答を確認する。

REQ-04: 削除（DELETE /api/v1/todos/:id）
操作: 画面上の削除ボタンから、対象のTODOを削除する。

入力: パスパラメータ id（1以上の整数）。

結果: 該当IDのレコードを削除し、ステータスコード 204（レスポンス本文なし）を返す。

エラー: id が1以上の整数でない場合は 400、該当IDが存在しない場合は 404、DB接続不可時は 503、サーバー内部エラー時は 500 を返す。

受け入れ条件: 削除操作後、画面およびDBから該当TODOが消去され、リロードしても再表示されないこと。

確認方法: 画面からTODOを削除し、一覧から消えること・再読み込み後も復元されないこと・存在しないID指定時に 404 が返ることを確認する。

3. 共通のデータ・エラー条件
データ仕様・共通フォーマット

バリデーション基準: title は前後空白除去後 1〜100文字、id は 1以上の整数 とする。

成功時レスポンス: 共通仕様に準拠する（一覧0件時は 200 で data: []、削除成功時は 204 で本文なし。具体的なJSONキー構造は「要確認」とし設計書で定義する）。

共通エラー条件（具体的なJSON構造は「要確認」とし設計書で決定）

400 Bad Request: JSON構文エラー、必須パラメータ欠落、パスパラメータ id の形式不正（数値以外や0以下など）。

422 Unprocessable Entity: バリデーション違反（トリム後の title が0文字または101文字以上、フィールドの型不一致など）。

404 Not Found: 指定された id に該当するTODOレコードが存在しない場合。

500 Internal Server Error: 予期しないアプリケーション例外やSQL実行エラーなど、サーバー内部の不具合。

503 Service Unavailable: Neon PostgreSQLへの接続タイムアウトやプール枯渇など、DBが利用できない状態。

4. 環境別確認
各環境において、既存の / と /api/db-check の正常稼働を維持した上で、/todo 画面および /api/v1/todos の全操作を確認する。

Local（ローカル開発環境）: ローカルサーバーを起動し、.env の DATABASE_URL 経由でNeon DBへ接続し、REQ-01〜04および各エラー（400/422/404）の挙動を確認する。

Preview（Vercel プレビュー環境）: プルリクエスト等のプレビューURL上で、Productionと同じNeon DBを参照しながら画面表示とCRUD操作が動作することを確認する。

Production（Vercel 本番環境）: 本番デプロイURL上で、架空データを用いて全機能の疎通確認およびリロード後のデータ永続化を確認する。
